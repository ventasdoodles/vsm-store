# PROMPT KIT - USAGE GUIDE

## Proposito
Este documento explica como usar el work-kit sin mezclar autoridad, contexto temporal y plantillas.
No reemplaza las reglas inmutables. Sirve como mapa de bootstrap y uso diario.

## Politica post-AGENTS.md
- Para Codex, empezar por `AGENTS.md` y cargar despues solo el canon/work-kit necesario para la lane.
- Para Antigravity, ChatGPT y handoffs largos, usar este work-kit como fuente canonica de roles, sizing, plantillas y contexto temporal.
- No usar presencia de `AGENTS.md` como prueba de automatizacion, runtime, produccion, DB/Supabase, provider, deploy, live smoke, auth/session/storage/secrets ni source/test behavior.
- Mantener separadas implementation, independent acceptance audit y canon reconciliation. El implementer no acepta su propio cambio.

## Modelo canonico de piezas
El work-kit queda organizado por funcion, no por estetica:

### 1. Metodo invariable
- Archivo: `docs/Reglas para IDE antigravity/PROMPT-SYSTEM-RULES-—-IMMUTABLE.txt`
- Uso: reglas estables del sistema de prompting.
- Cambia raramente.

### 2. Base operativa y handoff
- Archivo: `docs/Reglas para IDE antigravity/CONTEXTO-MAESTRO,-BASE-OPERATIVA-y-HANDOFF-CANÓNICO.txt`
- Uso: delimita roles, fronteras y lectura base del sistema.
- No debe llenarse de estado temporal.

### 3. Politica de sizing
- Archivo: `docs/Reglas para IDE antigravity/PROMPT_SIZING_POLICY_VSM_STORE.md`
- Uso: define cuanto contexto y detalle debe cargar cada prompt segun tipo y riesgo.
- No define estrategia de producto ni reemplaza constraints.

### 4. Contexto temporal vigente
- Archivo: `docs/Reglas para IDE antigravity/CONTEXTO_TEMPORAL_ACTUAL.md`
- Uso: memoria compacta del bloque activo.
- Debe actualizarse por bloque grande o por cambio real de frente.

### 5. Skill usage policy
- Archivo: `docs/Reglas para IDE antigravity/VSM_SKILL_USAGE_POLICY.md`
- Uso: define como Skills entran como procedimientos reutilizables.
- No es canon de producto, no reemplaza reglas, no autoriza scope extra y no convierte una lane high-risk en low-risk.

### 6. Biblioteca de plantillas
- Archivo: `docs/Reglas para IDE antigravity/PROMPT_LIBRARY_TEMPLATES.txt`
- Uso: redactar prompts concretos por tipo de tarea.
- No guardar aqui estado temporal.

### 7. Plantilla para renovar contexto temporal
- Archivo: `docs/Reglas para IDE antigravity/CONTEXTO-TEMPORAL-—-TEMPLATE.txt`
- Uso: crear o reemplazar el contexto temporal vigente.
- No usar como contexto vivo ni fuente activa por defecto.

### 8. Suplemento heredado Gemini
- Archivo: `docs/Reglas para IDE antigravity/ORQUESTACION-MAESTRA-GEM-y-HANDOFF-CANONICO.md`
- Uso: solo como puente heredado o consulta puntual para trabajos del ecosistema Gemini.
- No es el rector general del sistema ni fuente activa por defecto.

### 9. Guias suplementarias de flujo optimizado
- Archivo: `docs/Reglas para IDE antigravity/VSM_WORKFLOW_OPTIMIZATION_PROTOCOL.md`
- Archivo: `docs/Reglas para IDE antigravity/VSM_PHASE_COMBINATION_RISK_MATRIX.md`
- Uso: decidir cuando combinar fases, elegir flujo corto/medio/alto riesgo y evitar vueltas innecesarias sin mezclar responsabilidades.
- Incluyen el patron `Execution Block` para hasta 4 lanes LOW/MEDIUM relacionadas, siempre con WIP=1, acceptance independiente y canon despues de cada implementation commit.
- No reemplazan reglas inmutables, contexto maestro, sizing policy, contexto temporal ni plantillas.

## Skill-aware prompting

Las Skills son procedimientos operativos reutilizables. No reemplazan reglas, canon, prompt scope, role separation ni owner judgment.

Usar:

- `vsm-readiness` para roadmap, readiness, GO / NO-GO, priorizacion y prompt exacto.
- `vsm-implementation` para ejecutar cambios autorizados y validacion local dentro del scope.
- `vsm-acceptance-audit` para auditar diffs, commits o patches ya implementados sin corregirlos silenciosamente.
- `vsm-canon-reconciliation` solo despues de `ACCEPT`, `ACCEPT WITH RESIDUAL RISK` o autorizacion explicita del owner.
- `vsm-browser-visual-qa` solo cuando el prompt autorice navegador, entorno objetivo y alcance de evidencia.
- `vsm-high-risk-lane` para imponer fase separada en DB/Supabase, auth, secrets, deploy, payments, Product Search, Cesarin runtime, providers o live smoke.

El implementer no realiza independent final acceptance para high-risk work. Una Skill puede estrechar la ejecucion, pero nunca ampliar lo autorizado.

## Fuentes activas por defecto
- Default Codex: `AGENTS.md`, `AI_CONTEXT.md`, `AUDIT_LOG.md`, `STORE_FRONT_AI_PILOT_CONTEXT.md`, `README_WORKKIT.md` y `CONTEXTO_TEMPORAL_ACTUAL.md` cuando el snapshot temporal aporte valor.
- Default ChatGPT/Antigravity: reglas inmutables, contexto maestro, sizing policy, contexto temporal vigente y la plantilla concreta de la lane.
- Skill-aware prompts: cargar `VSM_SKILL_USAGE_POLICY.md` cuando el prompt invoque, cree o modifique Skills.
- Repo docs no-default: `CONTEXTO-TEMPORAL-—-TEMPLATE.txt`, `ORQUESTACION-MAESTRA-GEM-y-HANDOFF-CANONICO.md`, `VSM_WORKFLOW_OPTIMIZATION_PROTOCOL.md` y `VSM_PHASE_COMBINATION_RISK_MATRIX.md`. Mantenerlos disponibles, pero no cargarlos como fuente activa salvo que el prompt o la lane los necesite.

## Regla de autoridad rapida
- Lo inmutable manda sobre lo temporal.
- El contexto maestro manda sobre suplementos heredados.
- La politica de sizing regula el tamano del prompt, no su verdad.
- El contexto temporal nunca reabre lanes cerrados ni contradice el estado autoritativo actual.
- Las plantillas ayudan a escribir; no autorizan trabajo por si mismas.
- Las Skills ayudan a ejecutar procedimientos; no autorizan trabajo por si mismas.

## Flujo recomendado de uso
1. Identificar el tipo de tarea.
2. Cargar solo el bootstrap necesario para la lane.
3. Recortar el contexto con la sizing policy.
4. Escoger la plantilla correcta.
5. Completar mission objective, scope, constraints, output format y success condition.
6. Verificar explicitamente que no se reabra un frente congelado por arrastre de contexto viejo.
7. Enviar el prompt a la herramienta correcta.

## Cuando actualizar `CONTEXTO_TEMPORAL_ACTUAL.md`
Actualizar solo cuando:
- cambia la meta activa del bloque
- el frente anterior cierra de verdad
- cambia la naturaleza del trabajo
- hay una nueva restriccion autoritativa que afecta el siguiente handoff
- se canoniza un bloque importante y el snapshot queda stale

No actualizarlo por cada micro-cambio ni por ruido operativo menor.

## Nomenclatura normalizada
Usar estos nombres logicos al hablar del sistema:
- reglas inmutables
- contexto maestro
- sizing policy
- contexto temporal actual
- biblioteca de plantillas
- template de contexto temporal
- suplemento Gemini
- protocolo optimizado de flujo
- matriz de riesgo y combinacion

No inventar nombres alternos como `USAGE_GUIDE.md` o `PROMPT_SYSTEM_RULES_IMMUTABLE.md` si no son archivos reales del repositorio.

## Errores comunes a evitar
- meter todo en un mega-prompt infinito
- usar contexto temporal viejo como si fuera canon
- duplicar reglas en varios docs
- tratar el suplemento Gemini como autoridad general
- cargar plantillas o suplementos como fuentes activas por defecto
- saltarse la politica de sizing y sobrecargar prompts sin necesidad
